# 2.4 Diseñar una estrategia para cumplir con los requisitos de fiabilidad

> **Guía Oficial:** [[Guia AWS#Tarea 2.4: Diseñar una estrategia para cumplir con los requisitos de fiabilidad]]

## 🧠 Conceptos clave
- **Alta Disponibilidad (HA) vs Tolerancia a Fallos (FT):** HA significa que el sistema puede resistir que un servidor muera y redirigir el tráfico sin intervención humana (Ej. Multi-AZ). FT (Tolerancia a fallos) es un nivel superior, donde el sistema resiste el fallo sin la más mínima interrupción o impacto en el rendimiento para el cliente final.
- **Desacoplamiento (Loose Coupling):** La mejor manera de evitar que un componente defectuoso arrastre al resto del sistema. Si A llama directo a B y B se cae, A falla. Si A pone el mensaje en una cola y B lo procesa cuando puede, la caída de B no tumba a A.
- **Auto-sanación (Self-healing):** Diseñar asumiendo que el hardware fallará. EC2 Auto Scaling con *Health Checks* de un Load Balancer permite matar instancias enfermas y crear nuevas automáticamente sin que suene una alarma a las 3 a.m.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Integración de aplicaciones]])*

- **Amazon SQS / SNS / EventBridge:** La santa trinidad del desacoplamiento. SNS para notificar (Fan-out), SQS para retener carga de trabajo asíncrona, y EventBridge para reglas y orquestación de eventos de toda la nube.
- **AWS Step Functions:** Máquina de estado para flujos de trabajo largos, con capacidad nativa de reintentos (*Retries*) y captura de errores (*Catch*).
- **Amazon RDS / Aurora (Multi-AZ):** En base de datos, fiabilidad se traduce en activar Multi-AZ (la conmutación por error ante daño de hardware es gestionada por AWS).
- **Amazon ElastiCache (Redis/Valkey):** Para acelerar bases de datos, pero en alta disponibilidad requiere configuración Multi-AZ con *Automatic Failover*.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. SQS Estándar vs SQS FIFO
- **Estándar:** Escalamiento masivo e ilimitado. *Trade-off:* La entrega es "al menos una vez" (puede haber duplicados) y no se garantiza el orden de llegada ("Best effort ordering"). Tu aplicación receptora debe ser **idempotente** (resistente a procesar el mismo mensaje dos veces).
- **FIFO (First-In-First-Out):** Garantiza que los mensajes salgan en el mismo orden que entraron y "exactamente una vez". *Trade-off:* El Throughput (rendimiento) es bajo en comparación (hasta 30,000 req/s con batching habilitado) y cuesta más.

### 2. AWS Service Quotas
- Las cuotas son el peor enemigo de la fiabilidad si no las monitoreas. Un evento sorpresa puede disparar Auto Scaling y, si chocas contra el límite de EC2 de tu región (Service Quota), Auto Scaling fallará, y tu app caerá. El diseño dicta que debes usar **Amazon CloudWatch + Service Quotas** para generar alarmas cuando llegues al 80% de una cuota y pedir aumentos automáticamente.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. Lambdas colapsando a la Base de Datos (Connection Exhaustion)
* **La trampa:** Tienes un millón de eventos entrando y Lambda auto-escala a 1,000 instancias simultáneas. Cada Lambda abre una conexión directa al servidor de base de datos Amazon RDS. La base de datos colapsa porque se le acaban las conexiones concurrentes disponibles.
* **La configuración rebuscada:** La arquitectura fiable en Serverless contra bases de datos relacionales tradicionales **exige** el uso de **Amazon RDS Proxy**. El Proxy actúa como intermediario, agrupando (Pooling) las conexiones de las miles de Lambdas y traduciéndolas a solo unas decenas de conexiones reutilizables hacia la base de datos.

### 2. Mensajes venenosos (Poison Pill) en arquitecturas orientadas a eventos
* **La trampa:** Un usuario envía un JSON malformado. Tu instancia EC2 toma el mensaje de SQS, intenta procesarlo, falla por error de formato, y el mensaje vuelve a la cola. El proceso se repite infinitamente, consumiendo toda tu CPU y aumentando tu factura.
* **La configuración rebuscada:** Configurar siempre una **Dead Letter Queue (DLQ)**. En la cola de origen defines que, si un mensaje falla más de *X* veces (maxReceiveCount), sea expulsado automáticamente y enviado a la DLQ para que un desarrollador lo investigue manualmente.

### 3. Patrón Circuit Breaker en Step Functions / API Gateway
* **La trampa:** Tienes una arquitectura de microservicios. Un microservicio B externo está muy lento y el microservicio A (que lo llama repetidamente) se bloquea esperando (Timeouts masivos), colapsando toda tu aplicación en cascada.
* **La configuración rebuscada:** Si el examen pide evitar fallos en cascada, busca el patrón **Circuit Breaker** (Cortocircuito). Con **AWS Step Functions** puedes usar estados *Catch* para detectar fallos repetitivos y, si el servicio remoto no responde en unos segundos, Step Functions "abre el circuito" y activa un mecanismo alternativo (Ej. Devolver datos en caché guardados en DynamoDB) en lugar de seguir esperando y fallando.

### 4. Carencia de IPs (Subnet Exhaustion) bajo presión
* **La trampa:** Tienes todo en alta disponibilidad. Tu Auto Scaling empieza a lanzar servidores como loco por un pico masivo, pero AWS te tira un error de "Insufficient IP addresses" y el escalado falla.
* **La configuración rebuscada:** Esto ocurre porque definiste una subred demasiado pequeña (ej. /28, con 11 IPs libres). Para evitar este problema de diseño y solucionarlo sin rehacer la red, la mejor práctica en AWS es **Añadir un bloque CIDR IPv4 secundario a la VPC** y crear nuevas subredes más grandes, actualizando el ASG para que las utilice.
