# 2.1 Diseñar una estrategia de implementación para cumplir con los requisitos empresariales

> **Guía Oficial:** [[Guia AWS#Tarea 2.1: Diseñar una estrategia de implementación para cumplir con los requisitos empresariales]]

## 🧠 Conceptos clave y Estrategias de Despliegue
En este nivel, AWS asume que usas **Infraestructura como Código (IaC)** y que despliegas cambios de forma automatizada (CI/CD). Conocer las estrategias de despliegue y sus tiempos de *rollback* (restauración) es crítico:

- **All at Once (Todo a la vez):** Actualiza todos los servidores simultáneamente. *Trade-off:* Muy rápido, pero causa **Downtime** (tiempo de inactividad) total. Si falla, el rollback también causa downtime.
- **Rolling (Gradual):** Actualiza los servidores en lotes (ej. 2 de 10). *Trade-off:* Sin downtime, pero durante el despliegue la aplicación corre 2 versiones distintas a la vez (deben ser compatibles entre sí). Rollback es lento.
- **Immutable (Inmutable):** Lanza un grupo Auto Scaling (ASG) completamente nuevo detrás del balanceador con la nueva versión, y solo cuando está sano, elimina el viejo. *Trade-off:* Más seguro, requiere capacidad doble temporalmente.
- **Blue/Green (Azul/Verde):** Tienes dos entornos idénticos (Blue = Vivo, Green = Nuevo). El tráfico se desvía al Green. *Trade-off:* Cero downtime, y el **Rollback es instantáneo** (simplemente cambias el DNS o el Balanceador de vuelta al Blue). Requiere pagar por 2 entornos completos temporalmente.
- **Canary (Canario):** Mandas el 10% del tráfico al nuevo entorno. Si todo va bien, envías el resto. *Trade-off:* Excelente para mitigar riesgo de bugs que solo ocurren con tráfico real.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Herramientas para desarrolladores]] y [[Definicion servicios#Administración y gobernanza]])*

- **AWS CloudFormation:** Despliegue declarativo de infraestructura mediante código (YAML/JSON).
- **AWS CodePipeline:** Orquestador del flujo CI/CD.
- **AWS CodeDeploy:** Servicio especializado en inyectar el nuevo código a EC2, Lambda o ECS usando las estrategias mencionadas arriba.
- **AWS Systems Manager (SSM):** Especialmente *Run Command* y *State Manager* para aplicar configuraciones y parches a flotas gigantes de EC2 sin usar SSH.
- **AWS Elastic Beanstalk:** Servicio PaaS. AWS gestiona el despliegue, balanceo y auto scaling; el desarrollador solo sube el código (soporta Rolling, Immutable y All at once nativamente).

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Gestión Mutables (SSM) vs Inmutables (CloudFormation/ASG)
- **Mutable (Actualizar en el lugar con Systems Manager):** Tienes 50 servidores y usas SSM para instalar un parche en caliente. *Problema:* "Configuration Drift" (Deriva de configuración) donde los servidores poco a poco se vuelven diferentes (Snowflakes).
- **Inmutable (Actualizar reemplazando con AMI/CloudFormation):** Nunca editas un servidor corriendo. Creas una "Golden AMI" (Imagen maestra), cambias el CloudFormation/ASG y los servidores viejos mueren, naciendo nuevos perfectos. **AWS y el examen siempre prefieren la Inmutabilidad.**

### 2. Delegar en Servicios Administrados
Si el examen menciona "reducir la sobrecarga operativa", busca soluciones que migren cargas de EC2 (donde tú administras parches del SO) a **AWS Fargate** (contenedores sin SO) o **AWS Lambda** (Serverless puro).

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. CloudFormation StackSets (Despliegues Multi-Cuenta)
* **La trampa:** Tienes que desplegar un rol de auditoría de IAM y un bucket de S3 en 150 cuentas de AWS, y quieres automatizarlo asegurando que cualquier cuenta futura también los tenga.
* **La configuración rebuscada:** Usar **AWS CloudFormation StackSets** integrado con AWS Organizations. Un StackSet te permite lanzar un único *template* que se despliega automáticamente en las cuentas hijas (o en ciertas OUs) y en varias regiones simultáneamente. Y lo mejor: puede autodesplegarse si una cuenta nueva se une a la OU.

### 2. CloudFormation "Drift Detection" (Detección de Deriva)
* **La trampa:** Desplegaste un Security Group mediante CloudFormation. Un admin novato entró a la consola y abrió el puerto 22 a mano. CloudFormation no lo sabe y en el próximo despliegue pueden haber conflictos.
* **La configuración rebuscada:** Si te piden cómo identificar recursos que fueron modificados "a mano" por fuera del código, la respuesta es utilizar la función **CloudFormation Drift Detection**. Esto compara la configuración real vs la plantilla y resalta qué cambió. Para arreglarlo, lo ideal es importar el cambio al código y actualizar el stack, nunca hacer un rollback directo sin sincronizar.

### 3. Blue/Green en bases de datos (RDS)
* **La trampa:** Sabes hacer Blue/Green para los servidores EC2 usando el Balanceador, pero ¿qué pasa con la base de datos RDS que no puede tener "downtime" al cambiar la estructura de una tabla pesada?
* **La configuración rebuscada:** Amazon RDS y Amazon Aurora soportan entornos **Blue/Green nativos**. RDS crea un clon (Green) de la base de datos principal (Blue) usando replicación lógica. Haces los cambios lentos (ej. añadir un índice) en el Green sin afectar producción. Cuando estás listo, haces el *Switchover*: AWS detiene la escritura por unos segundos, asegura que Green esté sincronizado al 100%, renombra los endpoints y Green se vuelve Blue sin cambiar la cadena de conexión de tu aplicación.

### 4. CodeDeploy para AWS Lambda (Canary/Linear)
* **La trampa:** Quieres actualizar una función Lambda pero no quieres que el 100% de los usuarios la usen inmediatamente por si tiene un error.
* **La configuración rebuscada:** AWS CodeDeploy soporta despliegues de **Tráfico Gradual para Lambda**. Puedes usar `Canary10Percent5Minutes` (10% de tráfico va a la nueva Lambda, tras 5 minutos, si no hay alarmas en CloudWatch, se envía el 90% restante) o `Linear10PercentEvery1Minute` (envía 10% más cada 1 minuto hasta llegar a 100%). Esto se enlaza con CloudWatch Alarms para hacer **Rollback Automático Inmediato** si el código falla.
