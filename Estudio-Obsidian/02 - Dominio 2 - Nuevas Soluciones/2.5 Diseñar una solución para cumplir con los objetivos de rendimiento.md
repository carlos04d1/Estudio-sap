# 2.5 Diseñar una solución para cumplir con los objetivos de rendimiento

> **Guía Oficial:** [[Guia AWS#Tarea 2.5: Diseñar una solución para cumplir con los objetivos de rendimiento]]

## 🧠 Conceptos clave
- **Bases de Datos Especializadas (Purpose-built Databases):** El antipatrón más grande en AWS es usar una base de datos relacional (RDS) para todo. El rendimiento se maximiza usando la herramienta adecuada: Grafos (Neptune), Series de Tiempo (Timestream), Clave-Valor en microsegundos (DynamoDB), Analítica (Redshift).
- **Caché (Caching):** Patrón clave para aliviar la carga de lectura de las bases de datos. Si tu base de datos tiene 90% de lecturas y 10% de escrituras, un caché es obligatorio.
- **Búfer (Buffering):** Patrón clave para aliviar la carga de *escritura*. Si tienes picos donde te llegan miles de registros por segundo y tu base de datos se ahoga, pones una cola (SQS) o un stream (Kinesis) al frente para que actúe de amortiguador.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Computación]], [[Definicion servicios#Base de datos]] y [[Definicion servicios#Almacenamiento]])*

- **Amazon ElastiCache:** Motor de caché en memoria gestionado (Redis/Valkey o Memcached).
- **Amazon DynamoDB DAX (DynamoDB Accelerator):** Caché en memoria administrado *exclusivamente* para DynamoDB (reduce la latencia de milisegundos a microsegundos).
- **Almacenamiento EC2 (EBS):** Los volúmenes EBS dictan el rendimiento del disco. **gp3** (propósito general, IOPS independientes del tamaño) y **io2 Block Express** (para el máximo de IOPS y rendimiento de misión crítica).
- **Almacenamiento de Red:** **EFS** (para compartir archivos Linux a través de miles de EC2 concurrentes), **FSx for Lustre** (para cargas de computación de alto rendimiento HPC o Machine Learning).
- **Amazon Kinesis:** Plataforma para streaming, ingesta masiva de datos en tiempo real (Buffering).

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Redis/Valkey vs Memcached (en ElastiCache)
- **Memcached:** Multihilo, arquitectura hiper-simple. *Trade-off:* No soporta alta disponibilidad nativa (no tiene Multi-AZ), no soporta persistencia (si se reinicia, se pierde todo) y no maneja tipos de datos complejos.
- **Redis (o Valkey):** *Trade-off:* Es la opción dominante. Soporta tipos de datos avanzados (listas, sets, hashes), copias de seguridad, Pub/Sub, y **Alta Disponibilidad con Multi-AZ y Auto-Failover**. AWS en el examen casi siempre favorece Redis.

### 2. Patrones de Caché: Cache-Aside vs Write-Through
- **Cache-Aside (Lazy Loading):** La app pide el dato al caché; si no está, va a la BD, lo lee, y lo escribe en el caché. *Ventaja:* Solo almacena lo que realmente se usa. *Desventaja:* El primer usuario siempre sufre latencia (Caché miss) y el dato puede quedar obsoleto si no se le pone un buen TTL (Time-to-Live).
- **Write-Through:** La app escribe en la BD y simultáneamente en el caché. *Ventaja:* Los datos nunca están obsoletos y no hay penalización de lectura. *Desventaja:* Gastas memoria guardando datos que tal vez nadie lea jamás (Cache churn).

### 3. Familias de EC2 (Saber elegir)
Debes asociar letras a sus especialidades:
- **C (Compute):** Procesamiento en lote, servidores web intensivos, Machine Learning, HPC.
- **R / X (RAM):** Bases de datos en memoria, Redis, Memcached, bases de datos relacionales gigantes.
- **I / D (IOPS / Density):** Almacenamiento local ultrarrápido (Bases de datos NoSQL pesadas, Hadoop, Kafka).
- **M / T (General):** Para todo lo demás (Backend apps, servidores de prueba).

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. DAX vs ElastiCache para DynamoDB
* **La trampa:** Tienes una tabla DynamoDB y la app está sufriendo por alta latencia de lectura. El examen sugiere poner ElastiCache Redis frente a DynamoDB, pero esto requiere reescribir toda la lógica de lectura de tu aplicación.
* **La configuración rebuscada:** La respuesta óptima y de menor esfuerzo es **DynamoDB DAX**. Es compatible con la API de DynamoDB, por lo que no tienes que cambiar casi nada de código en la aplicación; DAX intercepta la llamada, responde en microsegundos si lo tiene, o va a la base de datos si no.

### 2. Red Exprimida al Máximo: Jumbo Frames, ENA y Placement Groups
* **La trampa:** Dos servidores EC2 `c5n.18xlarge` necesitan procesar modelos de Machine Learning transfiriendo gigabytes entre ellos con latencia mínima, pero la red estándar los está frenando.
* **La configuración rebuscada:** Para exprimir cada gota de rendimiento de red (HPC / ML):
  1. Activar el **Elastic Network Adapter (ENA)** o **EFA** (Elastic Fabric Adapter).
  2. Aumentar la MTU a 9001 (**Jumbo Frames**).
  3. Colocar a ambas instancias EC2 dentro de un **Cluster Placement Group**. (A diferencia de *Spread* que los separa para alta disponibilidad, *Cluster* los pone en el mismo rack físico para garantizar ancho de banda de hasta 100 Gbps).

### 3. Buffering de Clickstreams (IoT y Logs Masivos)
* **La trampa:** Lanzaste un juego móvil o dispositivos IoT y estás recibiendo 50,000 registros por segundo (clickstream) que intentas insertar directamente en Amazon RDS o Amazon S3. La base de datos colapsa.
* **La configuración rebuscada:** NUNCA escribas tráfico errático y masivo directo a una base de datos. Debes poner **Amazon Kinesis Data Firehose (Data Data Firehose)** frente a tus servidores. Firehose actúa como búfer, acumula los registros durante unos segundos o MBs, y luego hace una inserción por lotes (Batch Insert) masiva en S3 o Redshift, salvando el rendimiento del destino.

### 4. EBS Volumes IOPS limit: io2 Block Express vs instancias efímeras
* **La trampa:** Un cliente requiere garantizar 150,000 IOPS en un solo volumen de disco duro. `gp3` llega a 16,000 IOPS, y el examen sugiere montar un RAID 0 complejo con muchos discos.
* **La configuración rebuscada:** La solución directa (sin necesidad de administración de RAIDs y fallos) es usar la familia de discos **io2 Block Express**, que soporta hasta 256,000 IOPS y rendimiento SAN en la nube. Otra opción válida si los datos *no necesitan persistir* es elegir una familia de EC2 (tipo I3 o I4) con **Instance Store** (Discos NVMe soldados físicamente a la placa base del servidor) que ofrecen millones de IOPS gratuitos, pero se borran al apagar la máquina.
