# 2.3 Determinar los controles de seguridad en función de los requisitos

> **Guía Oficial:** [[Guia AWS#Tarea 2.3: Determinar los controles de seguridad en función de los requisitos]]

## 🧠 Conceptos clave
- **Defensa en profundidad (Defense in Depth):** No depender de una sola capa. AWS espera arquitecturas donde el tráfico pase por CloudFront (Perímetro global) → WAF (Capa 7 web) → NACLs (Nivel de Subred) → Security Groups (Nivel de Recurso) → IAM (Autenticación API).
- **Control de Flujo de Red:** En AWS el tráfico de red se permite explícitamente (deny por defecto). Si la red no es enrutable (no hay IGW o NAT), la instancia no puede salir. 
- **Gestión de Secretos:** Nunca incrustar contraseñas en el código, imágenes Docker o variables de entorno simples de Lambda. Se deben extraer en tiempo de ejecución usando servicios de gestión de configuración segura.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Seguridad, identidad y cumplimiento]] y [[Definicion servicios#Administración y gobernanza]])*

- **AWS WAF (Web Application Firewall):** Protege aplicaciones web frente a vulnerabilidades comunes (Inyección SQL, XSS, escaneo malicioso) y permite implementar cuotas (*Rate Limiting*).
- **AWS Shield:** *Shield Standard* es gratuito y protege contra ataques DDoS en capa 3/4. *Shield Advanced* cuesta 3,000$ al mes pero da protección contra DDoS a gran escala, soporte 24/7 de respuesta rápida (DRT) y reembolso por costos de escalado debido a ataques.
- **AWS Secrets Manager:** Almacenamiento seguro de secretos con la capacidad de rotación automática nativa.
- **AWS Systems Manager (Patch Manager & Parameter Store):** Gestión gratuita de parámetros seguros, y orquestador para aplicar parches de seguridad (OS patching) en flotas de EC2.
- **VPC Endpoints (PrivateLink):** Ya vistos en redes, pero en seguridad su objetivo es *evitar que el tráfico fluya por Internet* hacia servicios de AWS, anulando ataques de intermediario (Man-in-the-Middle) en la internet pública.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Security Groups (SG) vs. Network ACLs (NACL)
- **Security Groups:** Son *Stateful* (Con estado). Si permites tráfico entrante por el puerto 443, la respuesta de salida pasa automáticamente sin abrir otro puerto. Solo admiten reglas de PERMITIR (Allow).
- **Network ACLs:** Son *Stateless* (Sin estado). Operan a nivel de subred. Si entra tráfico por el 443, DEBES abrir explícitamente puertos efímeros de salida (1024-65535) para que la respuesta pueda salir. Admiten reglas de DENEGAR (Deny). *Uso principal en examen:* Denegar explícitamente IPs específicas maliciosas.

### 2. AWS Secrets Manager vs. SSM Parameter Store
- **Secrets Manager:** Tiene un costo mensual por secreto. *Súper poder:* Rota automáticamente las credenciales (por ejemplo de RDS) gracias a integraciones nativas con Lambda.
- **SSM Parameter Store:** Es gratuito (en nivel estándar). *Trade-off:* No puede rotar secretos automáticamente por sí solo (necesitarías crear tu propia lógica con EventBridge y Lambda).

### 3. AWS WAF asociado a ALB vs asociado a CloudFront
- **WAF en ALB (Application Load Balancer):** El ataque DDoS llega a tu región en AWS. Puede saturar recursos locales si el ataque es enorme.
- **WAF en CloudFront:** Absorbe el ataque a nivel global en las más de 400 ubicaciones perimetrales de AWS. Es la opción recomendada para aplicaciones web a gran escala expuestas públicamente.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. Proteger el origen de un ataque directo (Bypass de CloudFront)
* **La trampa:** Tienes un ALB protegido por CloudFront. Alguien descubre la IP pública directa de tu ALB y le manda un ataque DDoS, bypasseando por completo tu CloudFront y tu WAF.
* **La configuración rebuscada:** Configurar CloudFront para inyectar una cabecera HTTP personalizada secreta (Custom Header, Ej. `X-Shared-Secret: xyz`). Luego, crear una regla en el **WAF asociado al ALB** o directamente en el **Application Load Balancer (Listener Rules)** que bloquee cualquier solicitud que *no* contenga ese Header específico. (Otra opción es restringir el Security Group del ALB para que solo acepte IPs administradas de CloudFront usando las *AWS Managed Prefix Lists*).

### 2. Parcheo de seguridad cruzado (Patch Manager + Organizations)
* **La trampa:** Tienes 200 EC2 Linux y Windows repartidas en 15 cuentas de AWS diferentes y necesitas obligar a que se apliquen los parches críticos en un plazo de 7 días.
* **La configuración rebuscada:** Desde la cuenta de administración de AWS Organizations, usar **AWS Systems Manager Quick Setup** para desplegar agentes a toda la organización, y definir **Patch Baselines (Líneas base de parches)** centralizadas. Luego, programar "Ventanas de mantenimiento" (*Maintenance Windows*) para que ejecuten los parches sin intervención manual.

### 3. Asegurar un Bucket S3 solo para la red privada
* **La trampa:** Tienes documentos hiper-confidenciales en S3. Usas un VPC Endpoint para acceder desde las EC2 sin internet. Pero nada impide que alguien con credenciales IAM robe los datos desde su casa en el internet público.
* **La configuración rebuscada:** En la **Bucket Policy** de Amazon S3, debes crear una condición (`Condition: { "StringNotEquals": { "aws:sourceVpce": "vpce-1a2b3c4d" } }`) que haga un DENY a todo el acceso al bucket si la solicitud *no* viene físicamente desde ese VPC Endpoint exacto. Esto blinda el S3 a nivel de red, sin importar cuán altos sean los privilegios IAM del atacante.

### 4. IAM + Autenticación Web (Amazon Cognito + IAM Roles)
* **La trampa:** Un millón de usuarios descargaron tu app móvil y necesitan subir fotos directamente a S3. No puedes crear 1 millón de usuarios IAM. Tampoco debes enrutar los archivos grandes a través de tu EC2 porque colapsará.
* **La configuración rebuscada:** Usar **Amazon Cognito Identity Pools**. El usuario inicia sesión (con Facebook, Google o Email). Cognito le entrega **Credenciales Temporales de AWS (STS)** atadas a un Rol de IAM restringido, permitiendo al celular del usuario hacer *Upload directo* a S3 de forma segura y sin intermediarios (Direct-to-S3 Upload).
