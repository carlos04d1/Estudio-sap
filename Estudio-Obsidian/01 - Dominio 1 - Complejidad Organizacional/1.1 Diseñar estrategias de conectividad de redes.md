# 1.1 Diseñar estrategias de conectividad de redes

> **Guía Oficial:** [[Guia AWS#Tarea 1.1: Diseñar estrategias de conectividad de redes]]

## 🧠 Conceptos clave y segmentación de red
- **Infraestructura Global:** Selección de Regiones (por latencia o cumplimiento) y Zonas de Disponibilidad (AZs) para alta disponibilidad. Para ultra baja latencia se usan *Local Zones* o *AWS Wavelength* (para redes 5G).
- **Segmentación (VPC):** División mediante CIDR blocks. Uso de subredes públicas (rutas hacia Internet Gateway - IGW) y subredes privadas (sin acceso directo a internet, usan NAT Gateway o NAT Instances para salida).
- **DNS Híbrido:** Unificar la resolución de nombres entre las instalaciones físicas (on-premises) y AWS usando **Amazon Route 53 Resolver** (Inbound y Outbound endpoints).

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Redes y entrega de contenido]] para diferencias clave)*

- **Amazon VPC (VPC Peering):** Conexión 1 a 1 entre VPCs. **Ojo:** ¡No es transitivo!
- **AWS Transit Gateway (TGW):** Enrutador central (Hub-and-spoke) para interconectar miles de VPCs y redes on-premises. **Sí es transitivo**.
- **AWS Direct Connect (DX):** Conexión física y dedicada que evita el internet público.
- **AWS Site-to-Site VPN:** Conexión cifrada a través de internet usando IPsec.
- **VPC Endpoints (AWS PrivateLink):** Permite acceder a servicios de AWS (como S3 o DynamoDB) sin salir a internet público.
- **Amazon Route 53:** Resolvers para arquitecturas híbridas.
- **AWS Global Accelerator:** Enrutamiento a nivel global usando IPs Anycast estáticas.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. VPC Peering vs. AWS Transit Gateway
- **VPC Peering:** No tiene costo por hora, no tiene límite de ancho de banda y es fácil de configurar para 2 o 3 VPCs. *Problema:* A escala, crear una malla completa es inmanejable (fórmula N(N-1)/2).
- **Transit Gateway (TGW):** Simplifica masivamente la arquitectura (Hub-and-spoke) y escala fácilmente a miles de VPCs. *Problema:* Tiene costos por cada "attachment" y por los datos procesados, y tiene un límite de ancho de banda por attachment (50 Gbps).

### 2. Direct Connect (DX) vs. Site-to-Site VPN
- **Site-to-Site VPN:** Rápida de implementar (minutos), económica, pero dependiente de la latencia e inestabilidad del internet público. Límite de ~1.25 Gbps por túnel.
- **Direct Connect:** Ancho de banda consistente y alto (1 Gbps a 100 Gbps), latencia muy baja. *Problema:* Tarda semanas/meses en aprovisionarse físicamente y es costosa. No está cifrada por defecto (se debe usar MACsec o montar una VPN sobre DX).
- **Diseño Resiliente (El examen lo ama):** Usar dos conexiones DX para máxima fiabilidad, o un DX principal y una VPN como backup económico.

### 3. Gateway Endpoints vs. Interface Endpoints (PrivateLink)
- **Gateway Endpoints:** Solo existen para **S3 y DynamoDB**. Son **gratuitos**. Operan a nivel de tabla de enrutamiento. *Limitación:* No pueden ser accedidos desde on-premises a través de VPN/DX.
- **Interface Endpoints (PrivateLink):** Existen para casi todos los demás servicios. Operan mediante una Interfaz de Red Elástica (ENI) con IP privada. Tienen **costo** por hora y por GB. *Ventaja:* Pueden ser accedidos desde la red on-premises vía VPN/DX.

### 4. DNS Híbrido con Route 53
- **Inbound Endpoint:** Permite que los servidores on-premises consulten y resuelvan dominios alojados en la nube de AWS (ej. la IP interna de un RDS).
- **Outbound Endpoint:** Permite que las instancias en AWS consulten y resuelvan dominios de la red corporativa on-premises a través de reglas de reenvío (*Forwarding Rules*).

## 🛠️ Notas de resolución de problemas y supervisión
- **VPC Flow Logs:** Capturan la información del tráfico IP. Útiles para ver si el tráfico está siendo bloqueado (estado `REJECT`). 
- **Security Groups vs. NACLs:** Si el tráfico entra pero no regresa, es problema del NACL (stateless). Si no entra, suele ser el Security Group (stateful).
- **VPC Reachability Analyzer:** Analiza rutas de red entre un origen y un destino sin enviar paquetes reales. Perfecto para auditorías.


## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

En el nivel Profesional, el examen busca que conozcas configuraciones muy específicas y cómo encadenar servicios para resolver un requisito complejo. Presta atención a estos escenarios:

### 1. Cifrado extremo a extremo sobre Direct Connect (DX)
* **La trampa:** Te dicen que DX proporciona una conexión segura y privada, por lo que asumes que los datos van cifrados. ¡Falso! DX **no cifra** los datos en tránsito por defecto.
* **La configuración rebuscada:** Si el cliente exige "ancho de banda alto/consistente" (DX) Y "cifrado IPsec estricto" (VPN) simultáneamente, la solución correcta es **crear una AWS Site-to-Site VPN sobre una conexión Direct Connect** (usando una VIF pública o una VIF de tránsito). También puedes usar **MACsec**, pero solo si tus enrutadores físicos on-premises lo soportan (y la VPN siempre es la opción más apoyada en el examen si el hardware no se detalla).

### 2. Inspección de tráfico de terceros (Firewalls) a gran escala
* **La trampa:** El cliente quiere pasar todo el tráfico de 50 VPCs por unos firewalls de Palo Alto / Fortinet antes de salir a internet o entre VPCs. Configurar instancias EC2 con firewalls en cada VPC es una pesadilla de enrutamiento y escalabilidad.
* **La configuración rebuscada:** La mejor manera es usar un **Gateway Load Balancer (GWLB)** centralizado en una "VPC de Seguridad", integrado con **AWS Transit Gateway**. El GWLB usa el protocolo **GENEVE** para inyectar tráfico hacia las instancias EC2 del firewall de forma transparente, sin alterar los encabezados IP originales.

### 3. Conectar Direct Connect a Transit Gateway
* **La trampa:** Te preguntan cómo conectar tu centro de datos físico (mediante DX) a un Transit Gateway para hablar con múltiples VPCs. Si eliges crear una *Private Virtual Interface (Private VIF)*, la respuesta es incorrecta, porque un Private VIF solo se conecta a un VGW (Virtual Private Gateway) de una única VPC.
* **La configuración rebuscada:** Para conectar DX a un Transit Gateway, debes usar una **Transit VIF** conectada a un **Direct Connect Gateway (DXGW)**, el cual a su vez se asocia al Transit Gateway.

### 4. Route 53 Resolver a escala (VPC de Servicios Compartidos)
* **La trampa:** Tienes 100 VPCs que necesitan resolver nombres DNS de tu red on-premises. La opción incorrecta (por costos y mantenimiento) es crear Route 53 Outbound Endpoints en *cada una* de las 100 VPCs.
* **La configuración rebuscada:** Creas una **Shared Services VPC (VPC de servicios compartidos)** conectada al Transit Gateway. Colocas los Endpoints Inbound y Outbound de Route 53 **solo** en esta VPC central. Luego configuras reglas en Route 53 para que todas las demás VPCs utilicen este punto central para la resolución.

### 5. Acceso a S3 desde On-Premises sin internet
* **La trampa:** Para acceder a S3 sin internet usas un *VPC Gateway Endpoint*. Pero desde tu red on-premises vía Direct Connect, intentas usar ese Gateway Endpoint y falla, porque los Gateway Endpoints **no son accesibles desde fuera de su propia VPC** (no soportan DX ni VPN).
* **La configuración rebuscada:** La solución correcta es usar un **S3 Interface Endpoint (PrivateLink)** en lugar del Gateway Endpoint, el cual sí te da una IP privada resoluble y accesible a través de tu Direct Connect o VPN desde las instalaciones físicas.
