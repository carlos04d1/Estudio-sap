# 1.4 Diseñar un entorno de AWS de varias cuentas

> **Guía Oficial:** [[Guia AWS#Tarea 1.4: Diseñar un entorno de AWS de varias cuentas]]

## 🧠 Conceptos clave
- **Límite de Aislamiento (Blast Radius):** Una cuenta de AWS es el límite de aislamiento de seguridad, acceso y facturación más fuerte posible. Por eso, en arquitecturas profesionales, **nunca** se pone desarrollo, pruebas y producción en la misma cuenta; se usan múltiples cuentas.
- **Unidades Organizativas (OUs):** Agrupaciones lógicas de cuentas. **Regla de oro del examen:** Las OUs deben diseñarse en función de los *requisitos de seguridad y enrutamiento*, NO replicando el organigrama de recursos humanos de la empresa.
- **Gobernanza centralizada:** Establecer reglas estrictas ("Guardrails") desde una entidad padre que las cuentas hijas no puedan saltarse bajo ninguna circunstancia.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Administración y gobernanza]] y [[Definicion servicios#Seguridad, identidad y cumplimiento]])*

- **AWS Organizations:** Servicio fundacional. Permite agrupar cuentas, usar *Consolidated Billing* (facturación consolidada) y aplicar *Service Control Policies (SCPs)*.
- **AWS Control Tower:** Un servicio de mayor nivel que automatiza la creación de un entorno seguro ("Landing Zone") basado en mejores prácticas, usando Organizations por debajo. Configura OUs, CloudTrail central y reglas automáticas preventivas/detectives.
- **AWS RAM (Resource Access Manager):** Permite a una cuenta compartir recursos críticos (como Subnets de una VPC, AWS Transit Gateway o Licencias) de forma segura y directa con otras cuentas dentro de su Organization.
- **AWS CloudTrail (Organization Trail):** Habilidad de crear un rastro (Trail) a nivel de *toda* la Organización, que captura la actividad de las cuentas hijas de forma automática e inamovible.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. AWS Organizations (Hazlo tú mismo) vs AWS Control Tower (Gestionado)
- **AWS Organizations:** Te da las herramientas (SCPs, OUs), pero tú debes escribir los JSON de las políticas, tú debes configurar el CloudTrail central, tú debes vigilar la deriva (*drift*). Te da máxima flexibilidad pero es mucho trabajo manual de gobernanza.
- **AWS Control Tower:** Es un "paquete todo en uno". En un clic despliega cuentas centrales (Log Archive, Security) y aplica *Guardrails* (Ej. "Nadie puede borrar logs de CloudTrail"). Es la opción que AWS casi siempre recomendará en el examen para configurar entornos *nuevos* de múltiples cuentas (*Landing Zones*).

### 2. Consolidated Billing vs All Features
Dentro de AWS Organizations hay dos modos de activación:
- **Consolidated Billing:** Solo junta las facturas para aprovechar descuentos por volumen. No hay gobernanza.
- **All Features:** Es necesario habilitarlo para poder usar SCPs (Service Control Policies) y delegar administración.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. Centralización de Logs a prueba de manipulaciones
* **La trampa:** Tienes 50 cuentas y quieres asegurar que si la Cuenta 5 (Dev) es hackeada, el hacker no pueda borrar el rastro de CloudTrail para ocultar sus pasos.
* **La configuración rebuscada:**
  1. Habilitar **CloudTrail a nivel de Organización** (Organization-wide trail) desde la cuenta Master. Esto obliga a todas las cuentas miembro a registrar logs y *los usuarios de la cuenta miembro no pueden apagar este CloudTrail*.
  2. Enviar todos los logs a un bucket S3 que vive en una cuenta separada estrictamente aislada (**Log Archive Account**).
  3. Proteger ese bucket con S3 Object Lock (WORM) para que ni siquiera el Root pueda modificar los archivos log.

### 2. Compartir Redes Centralizadas (VPC Sharing con AWS RAM)
* **La trampa:** Tienes 10 aplicaciones, cada una en su propia cuenta de AWS. Todas necesitan conectarse a On-Premises vía Direct Connect. Configurar VPCs, Transit Gateways y VPNs en cada una de las 10 cuentas es caótico y costoso.
* **La configuración rebuscada:** Crear una **Network Account (Cuenta de Red)** central. Allí se crea la VPC principal conectada a On-Premises. Utilizando **AWS RAM (Resource Access Manager)**, la cuenta de Red *comparte las subredes privadas* (Subnet sharing) con las 10 cuentas hijas.
* *El detalle clave:* Las cuentas hijas verán esas subredes como suyas y podrán lanzar sus EC2 allí, administrando sus propios Security Groups, PERO no pueden cambiar las tablas de ruteo ni eliminar los Internet Gateways; eso solo lo controla la Cuenta de Red.

### 3. Delegación de seguridad (Security Hub y GuardDuty)
* **La trampa:** Tienes una cuenta Master de Organizations donde gestionas la facturación, pero le pides a tu equipo de Seguridad que entre allí a revisar Amazon GuardDuty y Security Hub. ¡Mala práctica! La cuenta Master debe usarse lo menos posible.
* **La configuración rebuscada:** Utilizar la característica de **"Delegated Administrator" (Administrador Delegado)**. Desde la cuenta Master, le delegas a una **Security Account** específica el control de servicios como GuardDuty, Security Hub, IAM Access Analyzer y Macie. El equipo de seguridad solo entra a su cuenta de seguridad, pero desde ahí tienen visibilidad de toda la organización.

### 4. Provisionamiento estandarizado de nuevas cuentas (Account Factory)
* **La trampa:** Un desarrollador necesita una cuenta nueva. Se la creas manualmente, pero olvidas bloquearle regiones fuera de USA o activar la encriptación.
* **La configuración rebuscada:** Si el examen menciona estandarizar y automatizar el ciclo de vida de cuentas para equipos internos, la respuesta suele involucrar **Account Factory** (una característica de Control Tower) que por debajo utiliza **AWS Service Catalog** para desplegar cuentas con VPCs pre-aprobadas y SCPs pre-asignadas.
