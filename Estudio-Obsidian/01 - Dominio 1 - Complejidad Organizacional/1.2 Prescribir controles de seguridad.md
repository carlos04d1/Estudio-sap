# 1.2 Prescribir controles de seguridad

> **Guía Oficial:** [[Guia AWS#Tarea 1.2: Prescribir controles de seguridad]]

## 🧠 Conceptos clave
- **Mínimo Privilegio (Least Privilege):** Regla de oro en AWS. Siempre comenzar sin permisos y otorgar solo lo estrictamente necesario.
- **Acceso entre cuentas (Cross-account):** En arquitecturas de múltiples cuentas, es preferible delegar accesos asumiendo roles (`AssumeRole`) mediante AWS STS, en lugar de compartir credenciales a largo plazo.
- **Federación de identidades:** Integración de AWS con directorios corporativos externos (Active Directory, Okta, Azure AD) usando SAML 2.0, o proveedores web públicos (Google, Facebook) usando OpenID Connect (OIDC).
- **Cifrado (En reposo y en tránsito):** En reposo se controla principalmente mediante **KMS** y **CloudHSM**. En tránsito, a través de certificados TLS gestionados por **ACM** e infraestructuras como VPN/MACsec.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Seguridad, identidad y cumplimiento]])*

- **AWS IAM & AWS STS:** Políticas, roles y credenciales temporales.
- **AWS IAM Identity Center (antes AWS SSO):** Para centralizar accesos a nivel de organización para usuarios corporativos.
- **AWS KMS (Key Management Service):** Gestión de claves de cifrado (simétricas/asimétricas) y control de accesos a ellas.
- **AWS CloudTrail:** El registro inmutable de *"quién hizo qué, desde dónde y cuándo"* (Llamadas a la API).
- **IAM Access Analyzer:** Detecta recursos de tu cuenta que están compartidos con cuentas o entidades externas.
- **Amazon Inspector:** Escaneo automático de vulnerabilidades a nivel de SO y paquetes en EC2 y ECR.
- **Amazon GuardDuty:** Detección de amenazas inteligente basada en machine learning (usa VPC Flow Logs, DNS logs, CloudTrail).
- **AWS Security Hub:** Agrega los hallazgos de Inspector, GuardDuty, IAM Access Analyzer y verifica el cumplimiento (ej. CIS Foundations).

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. IAM Users vs. IAM Identity Center (SSO)
- **IAM Users:** Son locales por cuenta. Difíciles de gestionar a escala. Generan *Access Keys* permanentes (riesgo de seguridad alto).
- **IAM Identity Center:** Se integra con AWS Organizations. Permite usar el directorio corporativo. Usa **credenciales temporales**. *Regla para el examen:* Si tienes más de 1 cuenta, la respuesta siempre es migrar a IAM Identity Center.

### 2. IAM Roles (Cross-account) vs. Resource-based Policies
- **IAM Roles:** El usuario debe invocar `sts:AssumeRole`. El usuario *pierde* sus permisos originales temporalmente mientras asume el rol de la otra cuenta.
- **Resource-based Policies (Ej. S3 Bucket Policy, KMS Key Policy):** El usuario en la cuenta A accede al recurso de la cuenta B *sin asumir un rol*. Mantiene sus permisos en la cuenta A. *Nota:* No todos los servicios soportan Resource-based policies, pero S3, SQS y KMS sí.

### 3. KMS Customer Managed Keys (CMK) vs AWS Managed Keys
- **AWS Managed Keys:** Son gratis, AWS rota las claves automáticamente cada 1 año. *Limitación:* No puedes usarlas de forma cruzada (*cross-account*).
- **Customer Managed Keys (CMK):** Tienen costo, te permiten definir las *Key Policies* (quién la puede usar) y son **obligatorias si necesitas compartir datos cifrados con otras cuentas AWS**.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. "Pase de rol" o PassRole
* **La trampa:** Tienes un desarrollador que puede lanzar instancias EC2, pero al intentar asociarle un IAM Role a la instancia, recibe un error de "Acceso Denegado", a pesar de tener el permiso `ec2:RunInstances`.
* **La configuración rebuscada:** Para que un usuario pueda asignarle un rol a un servicio de AWS (como EC2 o Lambda), el usuario necesita explícitamente el permiso `iam:PassRole` sobre ese rol específico. Esto evita la escalada de privilegios (que un usuario se asigne un rol de administrador a su propia instancia).

### 2. SCPs (Service Control Policies) vs IAM Policies
* **La trampa:** Aplicas una SCP en la Raíz de AWS Organizations que dice "Allow S3 Full Access", pero el usuario en la cuenta no puede acceder a S3.
* **La configuración rebuscada:** Las SCPs **nunca otorgan permisos**. Solo establecen un "límite máximo" (Guardrails). Si una SCP permite algo, el usuario *aún necesita* una política de IAM que se lo otorgue explícitamente. Sin embargo, si la SCP lo *deniega*, ni siquiera un usuario Root puede acceder a ese servicio.

### 3. Cifrado Cross-Account con KMS y S3
* **La trampa:** Tienes un bucket S3 en la Cuenta A. Un usuario de la Cuenta B sube un archivo. Luego, un administrador de la Cuenta A intenta leerlo y recibe "Acceso Denegado".
* **La configuración rebuscada:** En S3, por defecto, el objeto es propiedad de quien lo sube. Y si el objeto fue cifrado con una clave KMS de la Cuenta B, la Cuenta A no puede descifrarlo. **Solución:** 
  1. Habilitar `S3 Object Ownership` en "Bucket owner enforced" (para que el dueño del bucket sea dueño del archivo).
  2. Forzar (vía Bucket Policy) que todo objeto subido se cifre con una **Customer Managed Key (CMK) de la Cuenta A**.
  3. La *Key Policy* de esa CMK debe otorgar permisos de `kms:GenerateDataKey` a la Cuenta B.

### 4. Claves KMS Multi-Región
* **La trampa:** Quieres replicar una tabla de DynamoDB Global Table o un bucket S3 de `us-east-1` a `eu-west-1`. Usas una KMS CMK normal. Falla.
* **La configuración rebuscada:** Las claves KMS son estrictamente regionales. AWS no transfiere claves. Para replicar datos cifrados sin tener que descifrarlos y volverlos a cifrar en destino (lo cual rompe ciertos flujos), debes usar una **KMS Multi-Region Key**, que comparte el mismo *Key Material* en ambas regiones.

### 5. Detección de amenazas: Inspector vs GuardDuty vs Macie
El examen intentará confundirte sobre qué herramienta de seguridad usar:
* **Amazon Inspector:** Úsalo solo cuando te hablen de **"Vulnerabilidades de software (CVEs)"** o "Parches del SO y paquetes de red".
* **Amazon Macie:** Úsalo exclusivamente cuando te hablen de **"Datos sensibles, PII (Personal Identifiable Information), tarjetas de crédito"** dentro de Amazon S3.
* **Amazon GuardDuty:** Úsalo para **"Comportamiento anómalo"**, "Bitcoin mining", "Acceso desde IPs maliciosas conocidas" o "Llamadas a la API inusuales".
