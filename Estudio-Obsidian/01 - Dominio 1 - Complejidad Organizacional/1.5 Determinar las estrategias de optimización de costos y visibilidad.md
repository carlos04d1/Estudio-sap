# 1.5 Determinar las estrategias de optimización de costos y visibilidad

> **Guía Oficial:** [[Guia AWS#Tarea 1.5: Determinar las estrategias de optimización de costos y visibilidad]]

## 🧠 Conceptos clave
- **Dimensionamiento correcto (Right-sizing):** No pagar por capacidad que no se usa. En on-premises la infraestructura se sobredimensiona para picos (Capex); en AWS se debe adaptar dinámicamente a la carga real (Opex).
- **Visibilidad y asignación:** No puedes optimizar lo que no puedes medir. El uso de **Etiquetas de asignación de costos (Cost Allocation Tags)** es obligatorio para saber qué equipo, proyecto o centro de costos está gastando dinero.
- **Modelos de compra de cómputo:** On-Demand (Bajo demanda), Reserved Instances (RIs), Savings Plans, y Spot Instances.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Administración financiera en la nube]] y [[Definicion servicios#Administración y gobernanza]])*

- **AWS Cost Explorer:** Herramienta visual para ver gastos de los últimos 12 meses, predecir el futuro y ver recomendaciones de Savings Plans.
- **Informe de costo y uso de AWS (Cost and Usage Report - CUR):** El archivo más completo. Entrega datos hiper granulares (por hora/recurso) a un bucket de S3 para consultarlo con Amazon Athena.
- **AWS Budgets:** Configura umbrales de presupuesto y te alerta (por SNS o email) si se supera o si el pronóstico indica que se superará.
- **AWS Compute Optimizer:** Utiliza Machine Learning para analizar tus EC2, EBS y Lambdas históricos y recomendar si debes subir, bajar o cambiar la familia de las instancias.
- **Amazon S3 Storage Lens:** Da visibilidad en toda la organización sobre el uso de S3, identificando buckets enormes que no están usando *Lifecycle Policies* para abaratar costos (moviendo datos a Glacier).
- **AWS Trusted Advisor:** Tu consultor automático. Chequea costos (ej. EC2 sin uso, IPs elásticas huérfanas), seguridad, rendimiento, límites de servicio y tolerancia a fallos.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Reserved Instances (RIs) vs Savings Plans
- **Reserved Instances (RIs):** Te comprometes a un uso específico (Ej. tantas instancias `m5.large` en Windows en `us-east-1`). *Trade-off:* Son rígidas. Si cambias de arquitectura o base de datos, puedes quedar atado a pagar sin usar.
- **Savings Plans:** El modelo moderno. Te comprometes a un gasto monetario continuo (Ej. 10$ por hora durante 1 o 3 años). *Trade-off:* Son mucho más flexibles. El *Compute Savings Plan* aplica sin importar la familia de instancia, la región o si cambias de EC2 a AWS Fargate o Lambda. **El examen prefiere casi siempre Savings Plans sobre RIs para modernización.**

### 2. Spot Instances vs On-Demand
- **Spot Instances:** Hasta 90% de descuento aprovechando capacidad sobrante de AWS. *Trade-off fatal:* AWS te puede quitar la instancia con solo 2 minutos de preaviso. **Nunca** las uses para bases de datos principales o procesos monolíticos que no pueden interrumpirse. Úsalas para: procesamiento de imágenes, Big Data, colas SQS, contenedores sin estado (stateless).
- **Auto Scaling Mixto:** La mejor práctica es crear un Auto Scaling Group que mezcle un % de On-Demand (para la base segura) y un % de Spot (para picos económicos).

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. "Nadie usa las etiquetas de costos" (Tag Policies)
* **La trampa:** Tu empresa tiene *Cost Allocation Tags* ("Proyecto", "CentroCostos"), pero los desarrolladores olvidan ponerlas al crear recursos, lo que arruina el rastreo de facturación. Te piden la forma *menos restrictiva y más automatizada* de arreglarlo.
* **La configuración rebuscada:** Usar **AWS Tag Policies** integradas con AWS Organizations. Puedes configurar políticas que impidan a cualquier usuario de cualquier cuenta crear un recurso soportado (ej. EC2) si no incluye la etiqueta "CentroCostos" con un valor específico válido. (A esto se le llama cumplimiento proactivo).

### 2. Compartir descuentos entre cuentas (Discount Sharing)
* **La trampa:** La Cuenta de Producción compró un montón de *Savings Plans*, pero sobró capacidad comprometida. La Cuenta de Desarrollo usa On-Demand y está pagando precio completo. 
* **La configuración rebuscada:** En AWS Organizations con Facturación Consolidada (*Consolidated Billing*), el **uso compartido de descuentos de RIs y Savings Plans está activado por defecto**. AWS aplicará matemáticamente el descuento sobrante de Producción a Desarrollo. *El examen a veces te preguntará al revés:* ¿Cómo aislar los costos para facturar a clientes distintos? Y la respuesta será ir a la cuenta Master y **desactivar el "RI y Savings Plans discount sharing"**.

### 3. Cost Explorer vs. AWS CUR (Cost and Usage Report) + Athena
* **La trampa:** El director financiero quiere un análisis en profundidad cruzado con su propio software de BI de toda la organización a nivel de etiqueta, por hora, del último año y medio.
* **La configuración rebuscada:** AWS Cost Explorer no tiene ese nivel de granularidad profunda ni guarda datos más allá de cierto tiempo. La respuesta para "auditoría ultra detallada" es siempre generar el **AWS Cost and Usage Report (CUR)** en un bucket de S3, y usar **Amazon Athena** para hacerle queries con SQL y conectarlo a **Amazon QuickSight** o a su BI externo.

### 4. Apagar recursos que no se usan (AWS Instance Scheduler)
* **La trampa:** Los entornos de Dev y Test gastan dinero los fines de semana y las noches cuando nadie trabaja.
* **La configuración rebuscada:** Si el examen pide reducir costos drásticamente en entornos no productivos con el mínimo esfuerzo, buscar respuestas relacionadas con usar automatizaciones de EventBridge + Lambda o implementar la solución pre-empaquetada de **AWS Instance Scheduler** para apagar EC2 y RDS fuera del horario laboral (Ahorro del 70%).
