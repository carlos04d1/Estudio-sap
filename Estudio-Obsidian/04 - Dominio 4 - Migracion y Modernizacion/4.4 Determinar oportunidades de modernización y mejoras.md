# 4.4 Determinar oportunidades de modernización y mejoras

> **Guía Oficial:** [[Guia AWS#Tarea 4.4: Determinar oportunidades de modernización y mejoras]]

## 🧠 Conceptos clave
Esta es la fase culminante de la nube. Ya migraste, ya lograste Alta Disponibilidad y ya pusiste contenedores. La modernización y mejora de nivel arquitectónico superior (Nivel Dios en AWS) se trata de **inyectar Inteligencia, Analítica de Datos y automatización hiper-avanzada** a las aplicaciones heredadas para que hagan cosas que On-Premises eran imposibles.

- **Desacoplamiento Analítico:** Sacar la carga analítica pesada de tu base de datos transaccional (OLTP) y moverla a un Almacén de Datos (Data Warehouse - OLAP) o un Data Lake.
- **Inyección de IA (AI Services):** Usar los servicios gestionados de Machine Learning de AWS para que aplicaciones viejas puedan "ver", "escuchar" y "entender" sin necesidad de contratar científicos de datos.
- **Edge Computing Avanzado:** Mover el procesamiento al lugar donde se generan los datos físicos (fábricas, granjas, barcos) mediante IoT.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Análisis]] y [[Definicion servicios#Machine Learning]])*

- **Amazon Redshift & Amazon Athena:** Redshift para almacén de datos empresariales ultra rápido. Athena para hacer consultas SQL directamente a archivos de texto/CSV tirados en Amazon S3 sin servidores.
- **AWS Glue:** El servicio de ETL (Extraer, Transformar, Cargar) Serverless. Fundamental para preparar datos antes del análisis.
- **Servicios de IA de AWS:** *Amazon Rekognition* (análisis de imagen/video), *Amazon Textract* (extraer texto de PDFs escaneados), *Amazon Polly* (Texto a voz), *Amazon Comprehend* (Análisis de sentimientos).
- **AWS IoT Core & AWS IoT Greengrass:** Para conectar millones de dispositivos de hardware de forma segura y ejecutar código de AWS Lambda localmente en los dispositivos (Greengrass) aunque no tengan internet.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Data Lake (S3) vs Data Warehouse (Redshift)
- **Data Lake (S3 + Athena):** *Ventaja:* Infinitamente escalable y extremadamente barato porque guardas los datos crudos (JSON/Parquet) sin estructurar. *Desventaja:* Las consultas SQL con Athena cobran por Terabyte escaneado, no es óptimo para paneles de BI (Business Intelligence) en tiempo real con latencia sub-segundo.
- **Data Warehouse (Redshift):** *Ventaja:* Velocidad extrema para consultas estructuradas (Joints gigantescos) ideal para Amazon QuickSight o Tableau. *Desventaja:* Tienes que pre-procesar los datos (ETL) y el costo de clúster encendido es mucho mayor.

### 2. Machine Learning: IA Gestionada vs Amazon SageMaker
- **IA Gestionada (Rekognition/Comprehend):** AWS ya entrenó el modelo con millones de datos. Solo envías la foto por API y AWS te dice si hay un perro. *Trade-off:* Cero esfuerzo, pero no puedes enseñarle a reconocer un defecto de manufactura hiper-específico de tu fábrica de tornillos.
- **Amazon SageMaker:** Te da la infraestructura para que tus Científicos de Datos entrenen su propio modelo desde cero. *Trade-off:* Flexibilidad infinita, pero toma meses de desarrollo y talento humano muy caro.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. La Migración del Monolito Analítico
* **La trampa:** Tienes un Oracle On-Premises que hace transacciones de ventas y además los analistas financieros le corren consultas pesadas que congelan las ventas.
* **La configuración rebuscada:** Como Arquitecto, la mejora obligatoria es separar OLTP de OLAP. Migrar las transacciones a **Amazon Aurora** (usando SCT+DMS). Configurar **AWS Database Migration Service (DMS)** en modo continuo hacia **Amazon S3** (creando un Data Lake). Luego, usar **AWS Glue** para transformar los datos y cargarlos en **Amazon Redshift** para los analistas financieros, eliminando la contención de recursos.

### 2. Inyección de Inteligencia en procesos heredados (Paperless)
* **La trampa:** Una compañía de seguros recibe miles de reclamos en PDF por correo. Una EC2 vieja recibe los correos y 100 empleados humanos leen los PDF para escribir los datos en una base de datos.
* **La configuración rebuscada:** Modernizar con *Event-Driven AI*. El correo guarda el PDF en S3. Esto dispara una **AWS Lambda** que llama a **Amazon Textract** para extraer el texto estructurado (formularios) del PDF automáticamente, y usa **Amazon Comprehend** para saber si el tono del reclamo es "Furioso" o "Tranquilo". Finalmente, Lambda lo guarda en DynamoDB. Solo los casos dudosos pasan a revisión humana.

### 3. Computación en el Borde sin Internet (IoT Greengrass)
* **La trampa:** Tienes barcos petroleros en medio del océano con cientos de sensores de presión. Quieren usar AWS Lambda para analizar si hay peligro de explosión, pero el internet satelital es carísimo y se corta por días.
* **La configuración rebuscada:** Instalar **AWS IoT Greengrass** en un servidor industrial dentro del barco. Greengrass permite que el barco ejecute funciones **AWS Lambda locales** (Offline) y envíe alertas de hardware en tiempo real sin requerir internet. Cuando el barco llega al puerto y agarra Wi-Fi, Greengrass sincroniza los datos acumulados hacia **AWS IoT Core** en la nube de forma segura.

### 4. Búsqueda de registros a escala Exabyte (OpenSearch vs Athena)
* **La trampa:** Guardaste los logs de auditoría de toda tu empresa durante 10 años en Amazon S3. Necesitas buscar de inmediato en qué fecha un usuario específico hizo algo malo.
* **La configuración rebuscada:** Amazon OpenSearch es genial, pero cargar 10 años de logs a un clúster de OpenSearch costará millones. La estrategia correcta de modernización de análisis de logs "fríos" es **usar Amazon Athena**. Defines el esquema sobre tus logs en S3 (mejor si están en formato Parquet) y lanzas la consulta SQL estándar, pagando solo un par de dólares por esa búsqueda en lugar de tener servidores prendidos.
