# 4.1 Seleccionar estrategias de arquitectura y herramientas para las migraciones

> **Guía Oficial:** [[Guia AWS#Tarea 4.1: Seleccionar estrategias de arquitectura y herramientas para las migraciones]]

## 🧠 Conceptos clave
En el nivel *Professional*, AWS espera que actúes como un consultor en una migración de centro de datos hacia la nube. Lo primero que debe venir a tu mente son las **7 R's de la Migración**:

1. **Rehost (Rehospedar / Lift-and-Shift):** Tomar el servidor tal cual está y moverlo a una EC2 (rápido y fácil).
2. **Replatform (Reestructurar / Lift-tinker-and-shift):** Modificar un poco la app sin cambiar el código (Ej. Mover Tomcat a Elastic Beanstalk o MySQL a Amazon RDS).
3. **Refactor/Re-architect (Refactorizar):** Reescribir por completo la aplicación (Ej. Pasarla de un Monolito a microservicios Serverless con Lambda).
4. **Repurchase (Recomprar):** Abandonar tu software viejo y pasarte a un SaaS (Ej. Dejar tu Exchange Server viejo y pagar por Office 365 o WorkMail).
5. **Relocate (Reubicar):** Específico de VMware. Mover vSphere a VMware Cloud on AWS sin cambios.
6. **Retain (Retener):** Dejarlo on-premises porque es imposible de migrar o muy viejo.
7. **Retire (Retirar):** Apagarlo porque nadie lo usa.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Migración y transferencia]])*

- **AWS Application Discovery Service:** Herramienta para descubrir ("mapear") tu centro de datos físico antes de migrar. (Entender qué máquinas se conectan con qué base de datos).
- **AWS Application Migration Service (MGN):** El servicio definitivo para la estrategia **Rehost** (Migraciones a nivel de bloque sin tiempo de inactividad). Reemplaza al antiguo Server Migration Service (SMS).
- **AWS Database Migration Service (DMS):** Migra bases de datos en caliente con cero o mínimo *downtime*.
- **AWS Schema Conversion Tool (SCT):** Programa que traduce estructuras de tablas y funciones (Ej. De Oracle SQL a PostgreSQL).
- **AWS DataSync:** Servicio de transferencia masiva de archivos (NFS/SMB) a altísima velocidad a través de la red (por Internet o Direct Connect).
- **Familia AWS Snow (Snowball Edge / Snowmobile):** Maletas y camiones físicos cargados de discos duros para migraciones *Offline* gigantes.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Migración de Datos: Red (DataSync) vs Discos Físicos (Snowball)
- **Trade-off:** La regla de oro de AWS dicta hacer matemáticas simples: Calcula cuánto tardarás en subir los Terabytes usando el ancho de banda disponible de la empresa. **Si por red el tiempo de subida es mayor a 1 semana**, la respuesta correcta en el examen siempre será pedir un **AWS Snowball Edge**.

### 2. Descubrimiento: Agentless (Sin Agente) vs Agent-based (Con Agente)
- Cuando mapeas el centro de datos con AWS Application Discovery Service:
  - **Agentless (Sin Agente):** Es fácil, pero **solo funciona en VMware vCenter**. Te dice la CPU, RAM y espacio en disco.
  - **Agent-based (Basado en Agente):** Tienes que instalarlo en cada servidor Linux/Windows, pero es indispensable si necesitas mapear las **conexiones de red activas y los procesos** (saber si el Servidor A realmente habla con la Base de datos B).

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. La Migración Heterogénea de Base de Datos
* **La trampa:** Tienes un motor comercial costoso (Oracle o SQL Server) y la empresa quiere migrar a Amazon Aurora PostgreSQL (Replatform). El examen te pedirá los pasos exactos.
* **La configuración rebuscada:** NUNCA uses DMS solo. Primero, usas el **AWS Schema Conversion Tool (SCT)** que genera un reporte y traduce las funciones, *triggers* (disparadores) y esquema de tablas hacia el formato PostgreSQL en destino. *Segundo*, una vez el esquema está creado, usas **AWS DMS (Database Migration Service)** para mover la data en vivo (los registros) usando la replicación lógica.

### 2. Migración MGN sin Downtime (Zero Downtime Cutover)
* **La trampa:** El cliente exige migrar sus 50 servidores On-Premises pero afirma que el negocio no puede permitirse que estén caídos ni un solo minuto durante el proceso.
* **La configuración rebuscada:** Usar **AWS Application Migration Service (MGN)**. Se instala el agente y empieza la replicación a nivel de bloque hacia AWS en segundo plano, **mientras el sistema On-Premises sigue trabajando y recibiendo tráfico en vivo**. Durante la "Ventana de corte" (Cutover Window), simplemente detienes la base de datos On-Premises durante 5 minutos, AWS MGN sincroniza los últimos bytes, lanza las instancias EC2 automáticamente y Route 53 desvía el tráfico. El tiempo de inactividad final es de escasos minutos, no horas.

### 3. Migración de datos híbrida: Snowball + DataSync
* **La trampa:** Tienes 500 TB on-premises que debes subir, pero el archivo está en constante uso. Envías el Snowball con los 500 TB, el correo físico tarda 1 semana en llegar a AWS y durante esa semana los empleados on-premises crearon y editaron 2 TB más que no se fueron en la maleta. ¿Cómo los sincronizas?
* **La configuración rebuscada:** Integrar Snowball y DataSync. Cuando el Snowball Edge termina de ser volcado en S3, instalas un Agente de **AWS DataSync** en la empresa. Configuras el DataSync para que solo sincronice **los deltas (los archivos que han cambiado o se han creado nuevos)**, unificando finalmente todo en el S3 destino sin interrumpir el negocio.
