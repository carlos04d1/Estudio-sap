# 4.3 Determinar una estrategia para modernizar aplicaciones existentes

> **Guía Oficial:** [[Guia AWS#Tarea 4.3: Determinar una estrategia para modernizar aplicaciones existentes]]

## 🧠 Conceptos clave
Migrar un servidor a EC2 te lleva a la nube, pero **modernizarlo (Refactor)** es lo que te da los verdaderos beneficios financieros y de elasticidad de AWS. El objetivo es matar el monolito y abrazar los microservicios, el código sin servidor (*Serverless*) y los eventos (*Event-Driven*).

- **El Patrón del Estrangulador (Strangler Fig Pattern):** Nunca reescribas un sistema masivo de un solo golpe (Big Bang). La mejor práctica de modernización es poner un enrutador inteligente al frente y reemplazar el monolito viejo "pieza por pieza" mediante nuevos microservicios.
- **Serverless First:** La mentalidad que AWS premiará en el examen. Si algo se puede hacer con AWS Lambda o Fargate, debes elegirlo sobre EC2, porque reduce drásticamente el Costo Total de Propiedad (TCO) operativo (no hay que aplicar parches, no hay OS, escala automático).
- **Desacoplamiento Orientado a Eventos:** Pasar de arquitecturas donde el Servicio A llama al Servicio B (Sincrónico), a arquitecturas donde el Servicio A emite un "Evento" al aire y el Servicio B (y C, y D) reaccionan a él cuando pueden (Asincrónico).

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Computación]] y [[Definicion conectores#Contenedores]])*

- **AWS Lambda & Amazon API Gateway:** El dúo dinámico del Serverless. Lambda ejecuta código en respuesta a eventos (máximo 15 minutos). API Gateway provee la puerta HTTP.
- **Amazon ECS / Amazon EKS:** Orquestadores de contenedores (Docker).
- **AWS Fargate:** El motor de cómputo Serverless *para contenedores*. Ejecutas tu contenedor en ECS/EKS sin tener que provisionar ni parchear servidores EC2 por debajo.
- **Amazon EventBridge / SQS / SNS:** El sistema nervioso de la arquitectura moderna para desacoplar componentes.
- **AWS App2Container:** Herramienta que escanea aplicaciones (Java/ASP.NET) instaladas en servidores viejos y las empaqueta automáticamente en contenedores listos para ECS/EKS.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Lambda vs. Contenedores (Fargate)
- **AWS Lambda:** *Ventajas:* Escala a cero costo, facturación por milisegundo, hiper-elástico. *Trade-off (Limitaciones):* **Límite estricto de 15 minutos** de ejecución por solicitud. Solo soporta ciertos lenguajes nativamente (aunque admite Docker images limitadas). Puede sufrir de "Cold Starts" (Arranques fríos).
- **Contenedores en AWS Fargate:** *Ventajas:* Sin límite de tiempo (procesos de horas o días), portabilidad a otras nubes. *Trade-off:* Facturación basada en la CPU/RAM mientras el contenedor exista, aunque no esté procesando peticiones. Tardan unos 60 segundos en iniciar un nuevo contenedor frente a un pico de tráfico.

### 2. Orquestadores: Amazon ECS vs. Amazon EKS
- **Amazon ECS:** Desarrollado por AWS. *Trade-off:* Curva de aprendizaje muy suave, se integra perfectamente con roles de IAM, CloudWatch y ALBs de forma nativa. Te "ata" un poco al ecosistema de AWS (Vendor Lock-in).
- **Amazon EKS:** Basado en Kubernetes de código abierto. *Trade-off:* Curva de aprendizaje extremadamente empinada y compleja. **Sólo se elige en el examen si el cliente dice:** *"Nuestro equipo ya tiene mucha experiencia en Kubernetes On-Premises"* o *"Exigimos portabilidad total multi-nube sin depender de APIs propietarias de AWS"*.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. El Patrón Estrangulador con ALB / API Gateway
* **La trampa:** Tienes un monolito en EC2 enorme (`mi-tienda.com`) y el cliente quiere modernizar el módulo de facturación a una AWS Lambda, pero sin interrumpir al resto de la aplicación ni cambiar de dominio.
* **La configuración rebuscada:** Colocas un **Application Load Balancer (ALB)** o un **Amazon API Gateway** frente a todo. Configuras una regla de enrutamiento basado en la ruta (Path-based routing): Todo el tráfico `/*` va al monolito EC2 viejo, PERO el tráfico `/facturas/*` va directamente a la nueva función Lambda o servicio de contenedores. Con el tiempo, vas robándole rutas al monolito hasta que lo puedes apagar.

### 2. Evitar el dolor de la reescritura: AWS App2Container
* **La trampa:** Un cliente tiene 50 aplicaciones web en Tomcat (Java) o IIS (.NET) corriendo On-Premises. Quieren modernizarse a Contenedores en AWS, pero los desarrolladores originales ya no están en la empresa y no saben cómo crear los `Dockerfile` ni las tareas de orquestación.
* **La configuración rebuscada:** Usar **AWS App2Container**. Esta herramienta de línea de comandos se instala en el servidor origen; analiza los procesos de Java/IIS, extrae los binarios, genera automáticamente la imagen Docker, la sube a Amazon ECR y te crea las plantillas de CloudFormation para ECS listas para usar, todo sin tocar el código fuente.

### 3. Bases de Datos Modernas: Adiós a las Licencias
* **La trampa:** El cliente gasta millones en licencias de Microsoft SQL Server u Oracle. Tienen cargas de trabajo intermitentes (ej. un sistema de reservas que solo se usa fines de semana).
* **La configuración rebuscada:** En preguntas de "optimización radical por modernización", el camino recomendado por AWS es hacer una migración heterogénea (usando SCT+DMS) hacia **Amazon Aurora Serverless (PostgreSQL/MySQL compatible)**. Aurora Serverless v2 reacciona a los picos en fracciones de segundo y ahorra costos masivos cuando no se usa, liberando a la empresa de auditorías de licencias corporativas.

### 4. El límite de tiempo de Lambda para procesamiento por lotes
* **La trampa:** Un desarrollador migró un script de procesamiento de video a AWS Lambda, pero como procesar un video de 4K tarda 45 minutos, Lambda simplemente devuelve un error "Timeout" a los 15 minutos y falla.
* **La configuración rebuscada:** Lambda no sirve para procesos de larga duración. Si te exigen mantener la arquitectura sin servidor (*Serverless*), la respuesta correcta es migrar ese script a un contenedor Docker y ejecutarlo como una tarea (Task) en **AWS Fargate** (que no tiene límites de tiempo) o pasarlo a **AWS Batch**.
