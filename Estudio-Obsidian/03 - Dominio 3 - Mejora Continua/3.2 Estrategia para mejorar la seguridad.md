# 3.2 Estrategia para mejorar la seguridad

> **Guía Oficial:** [[Guia AWS#Tarea 3.2: Determinar una estrategia para mejorar la seguridad]]

## 🧠 Conceptos clave
En el Dominio 3, la seguridad trata de **auditar un entorno heredado o existente** y cerrarle los agujeros sin romper las aplicaciones que ya están en producción.

- **Mínimo Privilegio Retroactivo:** Los sistemas heredados suelen tener roles con `AdministratorAccess` o `*.*`. Tu objetivo es auditar qué permisos usan *realmente* y eliminar el resto de los accesos.
- **Trazabilidad Integral:** En arquitecturas antiguas nadie sabe quién borró qué. Tienes que habilitar registros (CloudTrail, VPC Flow Logs, DNS Query Logs) para poder hacer análisis forense.
- **Adiós a los "Bastion Hosts":** Tener un servidor "salto" (Bastion) con el puerto 22 abierto a internet, donde guardas las llaves SSH (`.pem`), es una arquitectura obsoleta y vulnerable.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Seguridad, identidad y cumplimiento]] y [[Definicion servicios#Administración y gobernanza]])*

- **IAM Access Analyzer:** Analiza el acceso matemático (quién de afuera tiene acceso a lo de adentro) y analiza logs históricos para recomendarte políticas ajustadas.
- **AWS Systems Manager (Session Manager):** El reemplazo de los Bastion Hosts y SSH. Permite acceder a las instancias de forma segura a través de IAM.
- **AWS Systems Manager (Patch Manager):** Automatiza el escaneo e instalación de parches críticos en los sistemas operativos.
- **Amazon Macie:** Usa Machine Learning para leer todos tus archivos en S3 y detectar si olvidaste números de tarjetas de crédito o pasaportes públicos.
- **AWS Config:** Para forzar reglas de cumplimiento continuo (Ej. obligar a que todos los discos estén cifrados).

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. SSH Tradicional vs. SSM Session Manager
- **SSH (Bastion Hosts):** *Trade-off:* Requiere abrir el puerto 22 en los Security Groups, debes administrar las llaves SSH, y es difícil auditar qué comandos ejecutó exactamente el administrador.
- **SSM Session Manager:** *Trade-off:* Requiere que la instancia EC2 tenga el Agente SSM instalado y rol IAM apropiado. A cambio, **no necesitas abrir puertos de entrada**, te autenticas con tus credenciales de IAM (o AWS SSO), y **puedes registrar cada tecla presionada** (logs de sesión) enviándolos inmutables a S3 o CloudWatch para auditoría.

### 2. Parchear (Patch Manager) vs. Reemplazar (Inmutabilidad)
- **Patch Manager:** *Ventaja:* No necesitas apagar el servidor web, aplica el parche en caliente. *Desventaja:* Si el parche corrompe el servidor, el rollback es doloroso.
- **Inmutabilidad (Recomendado):** Generas una nueva AMI (Imagen) con los parches ya aplicados. Usas EC2 Auto Scaling Instance Refresh para destruir los servidores viejos y levantar los nuevos. *Ventaja:* Siempre puedes retroceder a la AMI anterior en 5 minutos si algo sale mal.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. "Reducir los privilegios del Rol Dios (Admin)"
* **La trampa:** Heredas una aplicación Legacy. El Rol de IAM de la EC2 tiene la política `AdministratorAccess`. Si se la quitas, la app se rompe porque no sabes qué permisos necesita. Escribir la política a mano leyendo el código tomaría meses.
* **La configuración rebuscada:** Usar **IAM Access Analyzer (Policy Generation)**. Esta herramienta revisa el historial de **AWS CloudTrail** de los últimos 90 días, observa exactamente qué APIs de AWS llamó esa EC2 (Ej. solo llamó a S3 `GetObject` y DynamoDB `PutItem`), y **te genera automáticamente una política de mínimo privilegio** con formato JSON lista para aplicarse.

### 2. Detectar y Ocultar Tarjetas de Crédito en S3
* **La trampa:** Tienes un *Data Lake* gigante en S3 sin clasificar y el área de Cumplimiento (Compliance/PCI) exige saber si hay datos de tarjetas de crédito (PII) ocultos en millones de archivos de texto o logs.
* **La configuración rebuscada:** Activas **Amazon Macie**. Macie escanea masivamente el bucket usando expresiones regulares y Machine Learning. Si Macie encuentra datos PII, genera un evento (Finding) hacia **Amazon EventBridge**, el cual puede disparar una Lambda que le quite los permisos públicos a ese archivo o alerte al equipo legal.

### 3. Evitar cuentas huérfanas o claves no rotadas
* **La trampa:** Un empleado renuncia y sus credenciales estáticas de IAM (Access Keys) quedan activas por siempre porque nadie avisó.
* **La configuración rebuscada:** Para cuentas de usuario, usar **AWS Config Rules** con la regla `iam-user-unused-credentials-check`, que marque como `NON_COMPLIANT` las credenciales de más de 90 días de antigüedad, y asociarle una acción de remediación de Systems Manager para desactivar las llaves automáticamente. (Y como buena práctica superior, eliminar usuarios locales y forzar federación con **IAM Identity Center**).

### 4. Forzar Encriptación en todas partes sin romper nada
* **La trampa:** Una política de la empresa dicta que todos los volúmenes de EBS deben estar cifrados a partir de mañana.
* **La configuración rebuscada:** A nivel de cuenta (y por Región), puedes ir a los ajustes de EC2 y marcar la casilla **"Cifrado por defecto de EBS" (Default EBS Encryption)**. Esto asegura que cualquier intento futuro de crear un disco no cifrado será interceptado y forzado a cifrarse automáticamente con una clave KMS, sin que los desarrolladores tengan que cambiar sus plantillas de infraestructura as code. (Y para S3, activar el *Default Encryption* a nivel de bucket).
