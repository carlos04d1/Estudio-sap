# 3.3 Estrategia para mejorar el rendimiento

> **Guía Oficial:** [[Guia AWS#Tarea 3.3: Determinar una estrategia para mejorar el rendimiento]]

## 🧠 Conceptos clave
En la etapa de mejora continua, mejorar el rendimiento implica primero **detectar el cuello de botella** real mediante métricas, y luego **descargar (offload)** trabajo de los servidores principales trasladándolo a cachés, a la red periférica (Edge), o escalando de manera más inteligente.

- **SLAs y KPIs:** Traducir los requisitos del negocio a métricas de CloudWatch. Si el SLA exige que la página cargue en menos de 1 segundo (Latencia), el KPI es el percentil 99 (p99) del tiempo de respuesta del ALB, no el promedio.
- **Cuellos de Botella (Bottlenecks):** Pueden ser de CPU, de Memoria, de Red (Ancho de banda límite) o de Disco (Límite de IOPS en EBS).
- **Computación en el Borde (Edge Computing):** Acercar el procesamiento al usuario final para evitar viajes largos por internet hacia la región central de AWS.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Redes y entrega de contenido]] y [[Definicion servicios#Computación]])*

- **Amazon CloudFront:** CDN global. Mejora el rendimiento almacenando contenido en caché lo más cerca posible del usuario final.
- **Lambda@Edge / CloudFront Functions:** Permite ejecutar código (Node.js/Python) en las más de 400 ubicaciones perimetrales de AWS, quitando el procesamiento a los servidores EC2 centrales.
- **AWS Global Accelerator:** Enrutamiento a nivel mundial sobre la red troncal (backbone) de fibra óptica privada de AWS, proporcionando IPs Anycast estáticas.
- **Amazon EC2 Auto Scaling (y EC2 Fleet):** Orquestador de elasticidad. Responde a las métricas para inyectar más poder de cómputo.
- **Placement Groups (Grupos de ubicación):** Cómo colocas físicamente las instancias en el centro de datos de AWS afecta enormemente el rendimiento de red.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. CloudFront vs. AWS Global Accelerator
Ambos usan ubicaciones perimetrales (Edge Locations) para mejorar el rendimiento global, pero tienen propósitos distintos:
- **CloudFront:** Especializado en la capa 7 (HTTP/HTTPS). *Uso:* Caché de imágenes, videos y APIs REST web. *Trade-off:* Requiere que la aplicación hable HTTP.
- **Global Accelerator:** Especializado en capa 4 (TCP/UDP). *Uso:* Juegos online multiplayer, aplicaciones IoT que usan MQTT, o voz por IP (VoIP). *Trade-off:* No hace caché de contenido; acelera el viaje de los paquetes de red usando rutas optimizadas. Otorga dos IPs estáticas que nunca cambian, facilitando la lista blanca (allow-listing) en firewalls corporativos.

### 2. Auto Scaling basado en CPU vs Basado en Colas (SQS)
- **Escalado por CPU:** *Trade-off:* Es fácil de configurar, pero a veces la CPU engaña. Por ejemplo, una instancia puede estar esperando a una base de datos lenta (I/O Wait), la CPU estará baja y Auto Scaling NO lanzará más instancias, ahogando a los usuarios.
- **Escalado por SQS:** Escalar basado en la cantidad de mensajes pendientes (`ApproximateNumberOfMessagesVisible`) dividido por la cantidad de instancias. *Trade-off:* Refleja el trabajo real pendiente y acelera drásticamente el rendimiento en arquitecturas asíncronas.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. Descarga de procesamiento al Borde (Lambda@Edge)
* **La trampa:** Tienes servidores web (EC2) sobrecargados de CPU haciendo cosas simples como redimensionar imágenes (thumbnails) sobre la marcha, validando tokens de autenticación web (JWT), o decidiendo si mostrar la "Versión A" o la "Versión B" del sitio web (A/B Testing).
* **La configuración rebuscada:** ¡No escales los EC2! La arquitectura de mayor rendimiento es trasladar todo ese código a **Lambda@Edge** (o CloudFront Functions para tareas hiper rápidas). Esto valida el token o redimensiona la imagen a 10 milisegundos del usuario, antes de que el tráfico siquiera llegue a tocar tu servidor en AWS. Rendimiento máximo, menor costo de EC2.

### 2. El misterioso límite de IOPS y EBS-Optimized
* **La trampa:** La base de datos es lenta. Monitoreas las IOPS del disco EBS en CloudWatch y notas que ni siquiera llegan al máximo de IOPS (ej. disco io2). ¿Por qué va lento si el disco no está a tope?
* **La configuración rebuscada:** Las instancias EC2 también tienen un límite de **Ancho de banda de red hacia EBS (EBS-Optimized bandwidth)**. Si tu tipo de instancia EC2 (ej. `t3.micro`) tiene un límite de red hacia el disco inferior a lo que el disco puede entregar, el "cuello de botella" es la placa de red de la EC2, no el disco en sí. Solución: Cambiar a una familia de EC2 más grande o diseñada para alto rendimiento de disco (ej. familia `r5b` o `i4`).

### 3. Grupos de Ubicación en Clúster (Cluster Placement Groups)
* **La trampa:** Un clúster de Hadoop o de Machine Learning que consta de 10 instancias `c5n.18xlarge` no logra el rendimiento de red necesario para intercambiar petabytes de datos entre sí en tiempo real.
* **La configuración rebuscada:** De forma predeterminada, AWS lanza las instancias en un hardware aleatorio de su centro de datos. Para lograr hasta **100 Gbps de rendimiento de red entre instancias sin latencia**, debes configurarlas para que se lancen en un **Cluster Placement Group** (estarán ubicadas físicamente en el mismo estante de servidores).

### 4. Mantener SLA usando Instancias Spot (Spot Fleet)
* **La trampa:** Tienes un clúster de procesamiento de datos gigante donde necesitas mucho rendimiento de cómputo pero el presupuesto es mínimo. Tratas de usar Instancias Spot de la familia `c5.xlarge`, pero AWS te las quita frecuentemente y tu SLA de rendimiento se rompe por retrasos.
* **La configuración rebuscada:** Utilizar **Amazon EC2 Auto Scaling con "Capacity Rebalance"** o **Spot Fleet**, y configurar múltiples familias de instancias diferentes (Ej. `c5.xlarge`, `c4.xlarge`, `m5.xlarge`). Si AWS se queda sin stock de `c5`, el grupo lanzará inmediatamente de las otras familias, garantizando que siempre tengas poder de cómputo para mantener el rendimiento al máximo.
