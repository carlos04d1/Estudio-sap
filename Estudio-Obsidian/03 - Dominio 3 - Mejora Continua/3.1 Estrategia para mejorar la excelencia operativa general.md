# 3.1 Estrategia para mejorar la excelencia operativa general

> **Guía Oficial:** [[Guia AWS#Tarea 3.1: Determinar una estrategia para mejorar la excelencia operativa general]]

## 🧠 Conceptos clave
En el **Dominio 3 (Mejora Continua)** el enfoque del examen cambia: ya no estás diseñando un sistema nuevo en una hoja en blanco, sino que heredas un sistema existente (normalmente con problemas, caídas o procesos manuales) y debes mejorarlo.

- **Auto-corrección (Auto-remediation):** La excelencia operativa prohíbe el trabajo manual repetitivo. Si una alarma suena, no debe despertar a un humano si una máquina puede arreglarlo primero.
- **Observabilidad Completa:** Se compone de 3 pilares: **Métricas** (CPU/RAM), **Logs** (Qué falló en el código) y **Trazas** (Cómo viajó la solicitud entre 15 microservicios distintos).
- **Chaos Engineering (Ingeniería del Caos) / Game Days:** Práctica de inyectar fallos de forma intencional en los sistemas para verificar que las alarmas suenen y el Auto Scaling realmente funcione como se diseñó.

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Administración y gobernanza]] y [[Definicion servicios#Herramientas para desarrolladores]])*

- **Amazon CloudWatch:** El centro del universo operativo (Logs, Metrics, Alarms).
- **Amazon EventBridge (antes CloudWatch Events):** El router central de eventos. Conecta las alarmas de un servicio con las acciones de otro (Ej. Alarma -> EventBridge -> Dispara Lambda).
- **AWS Config:** Analiza la "Deriva" (Drift) de configuración contra una línea base deseada. (Ej. "Todos los discos EBS deben estar cifrados").
- **AWS Systems Manager (SSM):** Específicamente *SSM Automation* (Ejecuta flujos de trabajo de resolución automática de problemas) y *OpsCenter* (Centraliza los incidentes operativos o *OpsItems*).
- **AWS X-Ray:** Analiza y depura aplicaciones distribuidas y microservicios rastreando la petición del usuario de extremo a extremo.
- **AWS Fault Injection Service (FIS):** Herramienta gestionada para realizar experimentos de ingeniería del caos.

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Alertar a un Humano vs. Auto-Remediación
- **Alerta humana (SNS -> Email):** Es fácil de configurar, pero el RTO (Tiempo de recuperación) depende de cuánto tarde la persona en despertar, abrir la laptop y teclear el arreglo.
- **Auto-remediación (EventBridge -> SSM / Lambda):** Requiere escribir un script (Lambda) o un *SSM Automation Document*, pero el RTO se reduce a segundos o milisegundos. *Regla del examen:* Siempre prioriza la opción que automatice la reparación sin humanos.

### 2. CloudWatch Logs vs. S3 para almacenamiento de Logs
- **CloudWatch Logs:** Excelente para ingestión en tiempo real, generar alarmas basadas en palabras clave (Ej. la palabra `ERROR`) mediante *Metric Filters*, y análisis rápido con *CloudWatch Logs Insights*. *Trade-off:* Es caro para guardar terabytes durante años.
- **Amazon S3:** Ideal para retención legal a largo plazo (Ej. 7 años). *Trade-off:* No tiene alertas en tiempo real nativas. La mejor arquitectura exporta los logs caducados de CloudWatch a S3 de forma automática.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. Auto-remediación de Security Groups abiertos con AWS Config
* **La trampa:** Un desarrollador abre por error el puerto 22 a todo internet (`0.0.0.0/0`) en el Security Group de producción. Te piden la forma *más automatizada* de arreglar esto al instante sin depender de que un admin lo lea en un log.
* **La configuración rebuscada:**
  1. Habilitar **AWS Config** con una regla gestionada (ej. `restricted-ssh`).
  2. Cuando Config detecta el puerto abierto, marca el recurso como `NON_COMPLIANT`.
  3. Esto dispara una **AWS Config Remediation Action** que ejecuta un documento de **SSM Automation** subyacente.
  4. SSM borra automáticamente la regla del puerto 22 en segundos. El humano solo recibe una notificación de que "se cometió un error y ya se arregló".

### 2. El "Service Map" fantasma en microservicios
* **La trampa:** Un usuario hace clic en "Comprar" y el API Gateway responde lento. El API llama a Lambda, que envía un mensaje a SNS, que lo pasa a SQS, que es leído por Fargate, que inserta en DynamoDB. ¿Quién es el culpable de la lentitud?
* **La configuración rebuscada:** Imposible adivinarlo solo con los logs de CPU. Se debe instrumentar el código de todos los componentes con **AWS X-Ray SDK**. X-Ray genera un **Service Map (Mapa de servicios)** visual con nodos de colores que te indica exactamente, en milisegundos, en qué servicio del diagrama se estancó la solicitud (el cuello de botella).

### 3. Simulacros de fallos en Producción (Game Days) sin scripts caseros
* **La trampa:** El director quiere apagar aleatoriamente instancias de base de datos y reiniciar servidores web para ver si el equipo de operaciones reacciona bien. Escribir scripts manuales en Python para matar recursos es peligroso y difícil de detener si se sale de control.
* **La configuración rebuscada:** Utilizar **AWS Fault Injection Service (FIS)**. Este servicio te permite crear plantillas de experimentos (Ej. "agotar la CPU al 100% de las EC2 con la etiqueta 'Web' durante 5 minutos") y tiene **Condiciones de parada (Stop Conditions)** conectadas a alarmas de CloudWatch. Si el experimento rompe el entorno más de lo esperado, AWS FIS aborta y devuelve todo a la normalidad automáticamente.

### 4. Logging Centralizado Multi-Cuenta en tiempo real
* **La trampa:** Tienes 50 cuentas en AWS Organizations. Quieres ver los logs de aplicación de todas las cuentas en un solo lugar (una cuenta de Operaciones) *en tiempo real*.
* **La configuración rebuscada:** No exportes archivos a S3 si requieres tiempo real. Debes usar **CloudWatch Logs Destinations** (Destinos). Configuras las 49 cuentas hijas para que envíen sus streams de logs (usando Kinesis Data Streams como puente) directamente hacia la instancia de CloudWatch u Amazon OpenSearch ubicada centralmente en la Cuenta de Operaciones.
