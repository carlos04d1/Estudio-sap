# 3.4 Estrategia para mejorar la fiabilidad

> **Guía Oficial:** [[Guia AWS#Tarea 3.4: Determinar una estrategia para mejorar la fiabilidad]]

## 🧠 Conceptos clave
En este dominio el examen te presentará arquitecturas frágiles (Legacy) construidas como "monolitos". Tu trabajo será analizarlas, identificar los **Single Points of Failure (SPOF - Puntos Únicos de Fallo)** y arreglarlos.

- **De "Mascotas" a "Ganado" (Pets vs Cattle):** En sistemas antiguos, los servidores tienen nombre propio, configuraciones hechas a mano y si mueren, la empresa entra en pánico (Mascotas). La estrategia de mejora es convertirlos en "Ganado": servidores sin nombre en un Auto Scaling Group que mueren y se recrean idénticos automáticamente.
- **Sin Estado (Stateless):** Para poder matar y crear servidores libremente (escalado horizontal elástico), las máquinas **no pueden guardar estado local**. Las imágenes subidas por los usuarios deben ir a S3, y las sesiones de login deben ir a DynamoDB o ElastiCache, nunca al disco duro del EC2.
- **SPOF (Punto Único de Fallo):** Cualquier componente que, de apagarse, haga que todo el sistema colapse. (Ej: Un EC2 solitario, una base de datos sin réplica, un disco EBS).

## 🔌 Servicios involucrados
*(Ver [[Definicion servicios#Computación]], [[Definicion servicios#Base de datos]] y [[Definicion servicios#Almacenamiento]])*

- **Elastic Load Balancing (ALB/NLB) + Auto Scaling:** La combinación básica para curar un servidor EC2 que es SPOF.
- **Amazon EFS (Elastic File System):** Soluciona el problema de sistemas que requieren un disco duro compartido por red. Es nativamente Multi-AZ, eliminando el SPOF de usar un servidor NFS local.
- **Amazon RDS (Multi-AZ):** La solución de un solo clic para arreglar un motor de base de datos frágil.
- **AWS Cloud Map (Service Discovery):** Permite a los microservicios encontrarse por nombre dinámico en lugar de usar direcciones IP fijas (que cambian cuando el Auto Scaling mata una máquina).

## ⚖️ Decisiones de diseño (Trade-offs)

### 1. Sesiones de Usuario: Sticky Sessions vs DynamoDB/Redis
- **Sticky Sessions (Sesiones adhesivas en ALB):** Permite que el mismo usuario siempre vaya al mismo servidor EC2 donde se guardó su sesión en RAM. *Trade-off:* Es una solución rápida (cero cambios de código), pero arruina la fiabilidad. Si la instancia muere, el usuario pierde su carrito de compras y se desloguea.
- **Sesiones en DynamoDB o Redis (ElastiCache):** Extraer la sesión de la EC2 y guardarla en una BD externa ultra rápida. *Trade-off:* Requiere esfuerzo de refactorización de código, pero logra una arquitectura 100% *Stateless* y resiliente. Un EC2 muere y el usuario ni lo nota.

### 2. Discos EBS vs Amazon EFS
- **Amazon EBS:** *Trade-off:* Es extremadamente rápido, pero está confinado y "atrapado" en una sola Zona de Disponibilidad (AZ) y asociado a una sola máquina (salvo casos muy especiales). Es un SPOF regional natural.
- **Amazon EFS:** *Trade-off:* Es un sistema de archivos en red (NFS). Varios miles de instancias EC2 en múltiples AZs pueden leer y escribir simultáneamente en él. Es más caro y ligeramente más lento, pero elimina el SPOF del almacenamiento local.

## 🕵️ Escenarios avanzados y preguntas "rebuscadas" del examen

### 1. El Servidor FTP / NFS Monolítico que no se puede reescribir
* **La trampa:** Heredas una aplicación Legacy (Windows o Linux) gigantesca que requiere depositar archivos físicos en un disco "Z:\" o punto de montaje "mnt/share". La app tiene el código cerrado, no la puedes reescribir para usar Amazon S3 (API). Te piden hacerlo altamente disponible (HA) urgentemente.
* **La configuración rebuscada:**
  - Si es Linux: Migrar los datos a **Amazon EFS** y montar el EFS en el Auto Scaling Group.
  - Si es Windows: Migrar a **Amazon FSx for Windows File Server**.
  - Si el almacenamiento masivo está On-Premises pero lo necesitan subir a la nube como un disco local: Usar **AWS Storage Gateway (File Gateway)** para presentar un disco local en red (NFS/SMB) que por detrás envíe todo silenciosamente a S3 sin cambiar el código de la aplicación antigua.

### 2. Base de datos RDS "Single-AZ" bloqueando los backups
* **La trampa:** Tienes un RDS MySQL clásico corriendo en una sola AZ. Cuando la ventana de mantenimiento hace el backup automatizado, la base de datos se congela por unos segundos (I/O suspension) causando fallos en la aplicación.
* **La configuración rebuscada:** La estrategia obligatoria para fiabilidad y rendimiento de base de datos es habilitar **RDS Multi-AZ**. Al hacerlo, AWS toma el backup *desde la base de datos secundaria oculta (Standby)*, lo cual elimina por completo el impacto y la congelación de E/S en la base de datos principal de producción.

### 3. Eliminar IPs estáticas (*Hardcoding*)
* **La trampa:** Tienes una flota de Lambdas que llaman a una API antigua instalada en una EC2 grande. Para conectarse, los desarrolladores escribieron la IP pública de esa máquina (`54.21.x.x`) en el código de las Lambdas. Si la EC2 falla, tienen que lanzar otra y los devs deben cambiar el código de todas las Lambdas a mano.
* **La configuración rebuscada:** NUNCA permitas IPs fijas en el código. Solución: Crear una Zona Alojada Privada (*Private Hosted Zone*) en **Amazon Route 53** o un espacio de nombres en **AWS Cloud Map**. Pones un Application Load Balancer interno frente al EC2, y creas un **Alias Record** en Route 53 (ej. `api.interno.local`) apuntando al ALB. Las Lambdas solo llaman a ese nombre DNS.

### 4. Cuotas y Límites (Service Quotas) como causa de apagones
* **La trampa:** Tu arquitectura está lista y diseñada para escalar de 2 a 100 servidores. Inicia la campaña de marketing, pero tu app colapsa a los 20 servidores. 
* **La configuración rebuscada:** Nunca asumas que la nube es ilimitada por defecto. AWS impone límites (Ej. máximo de On-Demand vCPUs por región). La estrategia proactiva de fiabilidad exige monitorear con **AWS Trusted Advisor** o **Amazon CloudWatch integration con Service Quotas** para que te envíe una alerta automática por SNS cuando el uso de cualquier recurso cruce el 80% de la cuota, y solicitar proactivamente un aumento a Soporte de AWS.
